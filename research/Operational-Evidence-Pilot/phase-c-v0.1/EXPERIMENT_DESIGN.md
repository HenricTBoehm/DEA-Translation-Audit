# Design and executed controls

Each scenario receives a separate schema within an unprivileged, ephemeral PostgreSQL cluster. Test actors log in independently using random SCRAM credentials. TCP listens only on loopback. The launcher disables Unix sockets after a capability probe was rejected in this environment. One administrator provisions roles and schemas and can administer the server. The pilot logger is configured only after role passwords have been provisioned.

Native tables provide write-once-for-test-roles criterion versions, a protected score row x@1 = 0, and a singleton resolver binding. Threshold is 0 or 1. The selector executes native SQL UPDATE of the version column. A PostgreSQL trigger increments an epoch and records the authenticated SESSION_USER, previous/new version and transaction in the same successful selection transaction. FK and ACL constraints guard the version and role. Manufacturing an application claim alone creates no authorized selection. The observer's independent SQL session reads the actual server records and ACLs. Version rows retain digests and original authorship across a grant change.

The adjudicator submits a single SELECT of the evaluation function. Inside it, a statement joins the current resolver binding to its criterion and the sealed score, computes ge@1, and appends the evaluation result with exact version, epoch and digest. This is the mechanism's actual read and arithmetic, with no application-side replacement resolver. The committer calls a different function. That transaction locks the resolver row, checks the supplied checked pair against the recorded evaluation pair, checks the current pair against the evaluation pair, then inserts the decision. The lock stays through transaction commit. A distinct epoch detects intervening changes even if a name is selected again. End-to-end evaluation intentionally uses different statements/transactions; there is no claim of a system-global snapshot from preliminary check through commit.

| Control | Executed intervention | Checked result |
|---|---|---|
| C00 | Selector selects v0. Adjudicator checks/consumes v0. Separate committer finalizes. | Accept persisted for v0. Adjudicator commit and direct committer insert denied. |
| C01 | Writer publishes v1, tries to select it and to overwrite v0. | Both denied by ACL. Evaluation selects original v0 and persists accept. |
| C02 | Selector tries both publication and in-place edit, then selects v0 and v1 in separate operations under the same score. | Both write operations denied. v0 accepts and v1 rejects. Durable decision binds v1. Writer authored v1, selector activated it. |
| C03 | Writer publishes v1, admin revokes its publication grant, same writer attempts a new version, selector chooses old v1. | Later insertion denied, previously authorized v1 retained digest/author and is used. Reject persists. Server trace checks write→revoke→select→evaluate order. |
| C04 | First check v0 and consume v0 in a stale attempt, then select v1 before a different consumption from the earlier check. | Check/use mismatch rejected with 23514, stale use/current mismatch with 40001. Missing check rejected. No invalid decision persisted. Fresh v1 commit locks the resolver; concurrent selection ends with 55P03. Observer sees zero uncommitted decisions. After commit, selector changes active version to v0 and durable decision remains bound to v1. |

Diagnostic pairs in C02 and multiple attempted commits in C04 are controls inside those cases. Each case has one durable decision. An integrity result is not implementation of DEA-specific decision rules.
